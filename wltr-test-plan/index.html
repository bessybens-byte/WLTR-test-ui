How to use this plan

This is a black-box validation of WLTR's calibration analytics through its own user interface. Work top-to-bottom; each stage names the exact screen, the exact data to enter, and the exact result to expect on screen.

  • Everything happens in the browser. Open the WLTR web app (dev default http://localhost:3000, talking to the API at http://localhost:5000) and sign in. All navigation is via the left sidebar and on-page tabs and buttons.
  • Follow the chips. Sidebar = a left-nav destination · Tab = a tab within a page · Field = a form field · Button = a button you click.
  • Enter the data verbatim. Raw instrument text is provided as ready-to-paste files in ./rawdata/ (see the Appendix). You paste the whole file into a Raw text box — WLTR parses it; you never type individual peak areas.
  • Compare against the green boxes. Each Expected box states the value WLTR must display and the workbook cell it comes from. The app also prints that cell next to the field as a violet Excel↔UI hint, so you can confirm the mapping without leaving the screen.
  • Scope & starting state: a fresh WLTR database seeds only the permission roles and the configuration-driven root admin. Nothing else is pre-seeded — no laboratory, users, instrument, analytes, internal standards, calibration levels, or method config. You build the full chain first (Stage S) before the upload → group → compute → report → approve flow this plan validates.
  • When WLTR disagrees with a green box, record it as a product defect (with the screen, what you entered, and both values) — not as a tester error. The expected values are traced to the workbook and are the source of truth.
  • Gold values need the workbook's point trims. Stage 8 numbers (mean RF, %RSD, Acceptable) assume the same end-point exclusions the workbook analyst made (e.g. Bromomethane 13→10). Computing on all 13 levels first will not match those green boxes — complete Stage 6b before treating Stage 8 as a pass/fail gate.

Excel↔UI cross-reference mode

WLTR ships a built-in traceability aid that makes this plan largely self-checking. It is on by default in the dev build:

  • A dashed “Dev UI — Excel cross-reference mode” banner sits at the top of every page with a quick lookup of the most common UI hints → workbook locations.
  • A violet “Excel mapping” guide banner heads each major screen (upload, group compute, report card, summary report), naming the sheet(s) and where to look.
  • A small violet Excel↔UI · Sheet!Cell hint appears under individual fields and table columns, so the workbook cell in every green box below is also printed right on the control.
How to use it during testing. When a stage says “verify Summary!I57 = QIC”, you can confirm two things on screen: the value WLTR shows, and — via the field's Excel↔UI hint — that WLTR is pointing at a related workbook location. A value mismatch vs this plan's green boxes is a compute defect. A hint that cites a different cell than this plan (e.g. UI shows G10 while the plan cites J10 for the same RSD limit) is often a cover-page vs detail-layout difference — check both, and only flag a mapping defect if the meaning is wrong.

Full field-by-field map: docs/EXCEL_UI_FIELD_MAP.md. The banner may show a slightly different workbook filename suffix (e.g. …Unlocked (2).xlsm) — same preload family. If your build hides these hints, the plan still stands — the workbook cells are listed inline in every table.

SBuild the prerequisites

Do these once, in order, on a fresh database. Each screen returns an entity you reference later. Steps S.2 and S.5 are platform-level and need the root admin; everything else is done as the lab-admin user you create in S.4.

S.1 — Sign in as root admin

Open /login, enter the configured root-admin credentials from the API host's seed config (Seed:RootAdmin:Email / Seed:RootAdmin:Password — often root@example.com / Root#Admin123! in local harness scripts), and click Sign in. You land on Dashboard.

Credentials are environment-specific A 401 Unauthorized means this API instance was seeded differently — do not invent passwords. Read the API's launch config / run-api.ps1 env vars, or use a lab account that already exists on the instance. Platform-only steps (create laboratory, create technician for another user) still need a root/platform token.

S.2 — Create the laboratory (as root)

Laboratories ▸ New laboratory. Fill name/address/contact (e.g. “Aqua Env Labs”, Denver CO) and save.

S.3 — Invite a lab user, then accept

Invitations ▸ create an invite for analyst@aqua.test scoped to the new lab with the LabAdmin role.

Email note If email is disabled for local testing (AzureEmail:Enabled=false), the Invitations page shows the invite link / raw token directly. Open that accept-invite link, set password Analyst#123!, and submit.

S.4 — Create the Technician profile (as root)

First grab the invited user's Identity user id: open Users, find analyst@aqua.test (they must have accepted the invite), and copy their user id. Then Technicians ▸ New technician and paste it into Identity user id, with First name/Last name and Qualifications “VOC GC/MS”. A run cannot be uploaded until the acting user has a technician profile.

S.5 — Sign out, then sign in as the lab user

Use Sign out (bottom of sidebar), then sign in as analyst@aqua.test / Analyst#123!. All remaining setup and the entire test flow runs as this lab-scoped user, so laboratory scoping is automatic (no lab-ID prompts).

S.6 — Instrument, internal standard, analytes (as lab user)

  • Instruments ▸ New instrument: name GC/MS #4, type GC/MS.
  • Internal standards ▸ New internal standard: Name Fluorobenzene, Spike concentration = 10.
  • Analytes ▸ New analyte ×3 — set Name, Role = Target, and Default internal standard = Fluorobenzene for each: Dichlorodifluoromethane, Vinyl Chloride-C, Bromomethane.

If a raw name differs from the analyte name, resolve it later on the run detail page (Resolve analyte mapping, Stage 3) and tick Save as a lab-wide alias. Only the analytes you define are mapped — the other ~80 compounds per report are expected to stay unmapped (informational, not defects).

6bPoint inclusion & manual exclusions

How the workbook decides inclusion The workbook's point inclusion is not a formula. VBA macros behind command buttons write the chosen model and the number of included points (e.g. 11 of 13) per analyte; pre-generated LINEST/AVERAGE/STDEV formulas switch on those cells. In other words, an analyst trims the calibration range (drops the worst end levels) until the curve passes — an analyst-driven decision. WLTR mirrors this: you exclude points by hand and recompute.

Point exclusion lives on the Review tab under Regression input tables. Pick an analyte, then per calibration point you get an Exclude / Re-include action. Each row shows Amount ratio (X), Response ratio (Y), RF, predicted ŷ, residual, and % diff — use these to spot the worst end points (RF far from the mean, %Diff beyond ±20 %).

Worked example — Dichlorodifluoromethane (required for Stage 8 gold) Its all-points RF %RSD fails the 15 % average-model gate (live all-points often ≈ 29 %). Exclude deviant end levels until included points match the workbook's count (11 for Dichlorodifluoromethane, 12 for Vinyl Chloride-C, 10 for Bromomethane — see Stage 8 table), then recompute. Never trim below the method's Min points required.

To exclude: click Exclude on the point → choose a Reason (Manual exclude or % diff out of range) → type a required Note (audit justification) → Confirm exclude. Then return to Compute & model and click Compute calibration again.

What to confirm After excluding an end point and recomputing, the analyte's RF %RSD drops; if it now clears the limit, the Average (mean-RF) model becomes usable again — mirroring the workbook's 13→N point trims (e.g. Bromomethane 13→10). Recomputing marks prior results stale until you re-run; the report card and summary refresh from the new fit.

7Select a model per analyte

Approval requires every non-excluded target analyte to have a selected model. Two ways, both on Compute & model:

  • Bulk: the Calibration workflow card shows a Suggested variant (highest pass-count) with an Apply to all analytes button — one click selects it for every analyte.
  • Per analyte: in the report card table, click Select on the chosen variant row for that analyte. The row shows a green ✓ once selected.
Expected Selecting is confirmed by a toast and a ✓ on the row. Select per analyte to match the workbook: Bromomethane → Average RF; Vinyl Chloride-C → Quad (Inv Conct); Dichlorodifluoromethane → Quad (Inv Conct).
